## 4. 8 分钟四幕（每幕：结论 → 证据 → 数字 → 边界）

**第一幕 · 架构（90s）**
Scenario 契约：`build_scenario()` 返回工具/提示词/中间件/checkpoint/policy。换业务只加目录，不改运行时。
→ 11 个场景复用同一套运行时。

**第二幕 · 控制（120s）** —— 这里最能体现"做过 Agent"。
中间件顺序，讲**为什么**是这个顺序：
- 权限最外层：deny 的工具根本不进审批、不进超时、不执行；
- HITL 在超时外层：人思考的时间不算工具耗时；
- `ToolError` 在 `ToolRetry` 外层：重试耗尽了才把异常转成 error ToolMessage。

再讲**错误重注入**：参数非法不抛异常，而是回一条 `status="error"` 的 ToolMessage，让模型在下一轮自己改参数。这是 Agent 和普通 API 最大的区别——错误是 observation，不是崩溃。

**第三幕 · 决策（120s）**
planning policy：第一次模型调用前按规则注入 `route_to_*`，命中唯一规则就 `jump_to="tools"`；无命中/平局 **abstain**，交回模型。
为什么不用提示词：提示词不可验证；注入是可测、可审计的 Harness 决策，还省一次模型调用。
数字：router 12/12，baseline 11/12；平均模型调用 1.92 → 1.08。
更早的触发率实验：10 条 coding 任务，natural / routed 下 plan、subagent 都是 0/10；
不是机制坏了，是模型不会自发用。加 planning policy 后 eligible 3/10 → 3/3 触发。
边界：规则级，12 条小样本，不是语义 planner。

**第四幕 · 评测（180s）** —— 讲第 5 节那个故事。
三层：capability（直接调工具）/ behavior（跑完整 Agent 看工具选择与传参）/ outcome（跑完看环境）。
加 pass^k（3 trial）+ 5 类故障注入 + gate。

**收边界（30s）**：评测样本小、没接 CI、planner 还是规则级；多模态/多 Agent handoff/生产服务都没有。

## 5. 必须讲的反例（全项目最值钱的一段）

> router 这一组，**行为层 3/4，outcome 层 4/4**。
> 行为层看最终回答有没有覆盖期望词，有一条判失败；但 outcome 层去看 `route_to_research` 返回的 `target` 对不对、`target_trace_id` 在 trace 文件里存不存在——四条全对。
> 也就是说那次任务其实成功了，是我的行为评分误判了。
>
> 反过来更危险：回答里说"已保存"，但文件根本没写——关键词评分会给你一个假阳性。
> 所以我加了 outcome 断言：每条用例用 `run_id` 生成唯一内容标记，运行前快照目录，运行后检查文件内容、SQLite 行、任务图状态、路由 trace。**不看回答，看环境。**

收尾金句：

> **Transcript 可以撒谎，Outcome 不会。**
