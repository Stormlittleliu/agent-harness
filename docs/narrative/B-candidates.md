## 1. BFCL 参数语义（prompt 层）

- **现象**：`simple_python_13/15/16` 把 `x**2` 写成 `x^2`，3/3 trial `wrong_args`。
- **归因**：工具选对、结构对，错在参数值语义；schema 只校验“是字符串”，抓不到。
- **改动**：工具描述/提示说明 Python 表达式；不动校验器。
- **数据**：55/60 → 59/60；加重复调用抑制后 60/60；隔离实验“只加校验器”56/60 且回归 4 条。
- **升格实验**：只说“参数用 Python 语法”只修 13（15/16 仍错）；改成“题面记号只描述意图，参数必须能被 Python 执行”后 3 条都 3/3（3 case ×3 trial，未重跑 60 条）。
- **代价**：60 条抽样、stub 工具、简化评分；提示与抑制混在一起，单独贡献未隔离。
- **选它的理由**：最能展示“看 badcase → 分层归因 → 隔离实验”。
- **风险**：容易被认为只是“调了一句 prompt”。

## 2. FAQ 切块（数据/检索层）

- **现象**：`sb-rag-001/006/010` 期望故障/保养/选购源文件，top-k 被 100问 宽泛块占据。
- **归因**：1000 字 chunk 混了多条问答，单条事实语义被稀释。
- **改动**：按 `1. / 2.` 编号边界切块；其他文档不变。
- **数据**：检索 7/10 → 10/10；chunks 78 → 835；全量 selfbuilt 22/26 → 26/26（1-trial）。
- **代价**：chunk 数约 10 倍，embedding/检索成本上升；26/26 还叠加了 `sb-multi-005` 的 remember + prompt，不能全归因。
- **选它的理由**：非 prompt 优化，有明确数据前后对照。
- **风险**：source hit 不等于回答质量；1-trial 不是稳定性。

## 3. Planning policy（中间件/决策层）

- **现象**：12 条路由，模型自主 11/12；“请记住：我喜欢简洁的回答”直接回答，没路由。
- **归因**：路由是确定性决策，交给模型就不稳定，也没有可审计记录。
- **改动**：第一次模型调用前按规则注入 `route_to_*`；唯一命中才注入，平局/无命中 abstain。
- **数据**：11/12 → 12/12；1 条 abstain 后模型仍路由正确；平均模型调用 1.92 → 1.08；trigger 实验 natural/routed 0/10，policy eligible 3/3。
- **代价**：12 条小样本、规则级；目标场景真跑，时延可能更长，不能讲“更快”。
- **选它的理由**：最能说明“Harness 决策”，不是 prompt 优化。
- **风险**：会被追问“这不就是规则路由吗”——是的，边界要主动说。

## 4. Outcome 评测（评测口径）

- **现象**：router 行为层 3/4，outcome 层 4/4；行为失败是回答没覆盖期望词，但路由 target 和 trace 都对。
- **归因**：关键词评分在测“回答像不像”，不是“任务成没成”。
- **改动**：跑完看文件 / SQLite / 任务图 / 路由 trace，用 `run_id` 唯一标记 + 运行前快照。
- **数据**：12 条用例 / 13 个断言，3-trial pass^k 12/12；行为层对照 3/4。
- **代价**：断言手写；覆盖可检查副作用，不是开放域质量。
- **选它的理由**：金句“Transcript 可以撒谎，Outcome 不会”；最能体现评测判断力。
- **风险**：不是“指标提升”，是“指标换了”；要讲清为什么换。

## 5. Judge 不覆盖硬失败（评测安全）

- **现象**：旧逻辑 `passed = judged.verdict`，judge 说“回答不错”就能把工具没调、参数错翻成通过。
- **归因**：judge 应该只判语义覆盖，不该覆盖确定性硬失败。
- **改动**：`passed = deterministic_passed and judge_pass`；新增 `judge_pass` 字段和回归测试。
- **数据**：无性能数字；测试 `test_judge_cannot_override_deterministic_failure` 通过；全量 408 passed。
- **选它的理由**：P0 安全修复，展示“评测本身也会骗人”。
- **风险**：没有指标前后对照，故事偏机制。

## 6. Catalog 重建（工程/目录）

- **现象**：manifest 停在 8 源/320 条；`--list` 要扫全量数据，看起来卡死；新增 3 个 adapter 不在目录。
- **归因**：`--list` 调 `adapter.load()`；`git_version` 每条任务跑一次 git；无进度/失败隔离。
- **改动**：`--list` 只查可用性；build 每源 flush、失败跳过；`git_version` 按仓库缓存；来源数动态。
- **数据**：8 源/320 → 11 源/132；`--list` 秒回；manifest 带 `source_count` / `by_runner`。
- **选它的理由**：工程化、可复现、能解释“为什么以前构建会挂”。
- **风险**：没有模型能力提升，纯工程故事。

## 7. Trace 链路（可观测）

- **现象**：planner 旧报告没有 trace_id；workflow outcome 没 trace；重跑还暴露 `call_tool` JSON 插值 bug。
- **改动**：planner 写 `trace_id`；WorkflowRuntime 接 tracer；outcome 存 `trial_trace_ids`；修 JSON 转义。
- **数据**：workspace 15/15、planner 24/24、outcome 40/40；重跑后 outcome 12/12。
- **选它的理由**：能回答“结果怎么追溯到原始运行”。
- **风险**：偏基础设施，缺少“能力提升”叙事。

## 组合建议

| 时长 | 建议组合 |
|---|---|
| 5 min | 1（BFCL）+ 4（Outcome） |
| 10 min | 1 + 2 + 3 |
| 15 min | 1 + 2 + 3 + 4 |
| 20 min+ | 再加 5 或 6，按岗位选 |

**如果只选两条**：1 证明“会把指标改好”，4 证明“会怀疑指标本身”。
**如果岗位偏 Agent 运行时**：3 必须讲。
**如果岗位偏数据/检索**：2 必须讲。
**如果岗位偏平台/工程**：6 + 7。

## 不要讲成什么

- 不要把 1 讲成“BFCL 官方 60/60”；
- 不要把 2 的 26/26 全归因给切块；
- 不要把 3 讲成“自主 planner”或“更快”；
- 不要把 4/5 讲成“指标提升”，它们是口径/安全修复；
- 不要把 6/7 讲成模型能力提升。
